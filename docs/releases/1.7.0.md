## Implantação

1. Aplicar `alembic upgrade head` no ambiente de destino, com a conexão de
   migration autorizada. `20261115_01` sucede `20261114_01` e cria
   `password_reset_tokens` e seu índice por usuário. Não executar DDL manual.
2. Após a migration, aplicar como administrador o script revisável
   `scripts/sql/170-acesso-api.sql`, que inclui SELECT/INSERT/UPDATE em
   `password_reset_tokens` para `undb_api`. A API mantém as permissões existentes
   de sessão/usuário; não recebe DELETE nos tokens nem privilégios administrativos.
   Conferir o papel efetivo de runtime antes de liberar o fluxo. O script foi
   preparado nesta release, sem executar GRANT em ambiente operacional.
3. Publicar backend e frontend compatíveis. Conferir `FRONTEND_URL`, domínio
   remetente e adaptador de e-mail já configurado; o modo console é somente de
   teste local e não comprova entrega externa. Não expor tokens em evidências.
4. Verificar recuperação real com conta de teste controlada: e-mail recebido,
   link válido, rejeição após uso/expiração, troca e acesso com a nova senha.
5. Verificar `/robots.txt`, `/sitemap.xml`, fragmentos e amostras públicas de
   professor/disciplina por HTTPS, incluindo canonical, imagem OG e noindex de
   conta/avaliação. Cache compartilhado do XML pode durar até uma hora.
6. Conferir uma prévia real no WhatsApp após publicação e investigar cache
   externo antes de trocar a arte. Com acesso do responsável ao Search Console,
   verificar a propriedade existente, enviar sitemap e inspecionar URLs.

As etapas operacionais acima ainda não foram executadas para esta candidata.
Não foi criada tag/release nem enviado conteúdo em canais externos nesta preparação.

## Reversão e pós-merge

O downgrade da migration remove tokens de recuperação pendentes, fazendo com que
esses links deixem de funcionar. Não restaura senhas anteriores nem sessões já
invalidadas; esses efeitos são deliberados e não devem ser revertidos por edição
manual. Antes de downgrade, coordenar a versão da API para não manter endpoints
escrevendo na tabela removida. Backup e janela operacional seguem os procedimentos
vigentes; esta PR não executa nenhuma reversão.

Após revisão/merge humano, criar a tag no commit integrado quando autorizado e
retornar a preparação da release para develop conforme o Gitflow. Não fechar
#254, #166 ou #168 apenas por promover o código; manter os itens de validação
publicada, participantes e aceite ainda não comprovados.
