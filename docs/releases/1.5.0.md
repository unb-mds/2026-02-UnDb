# Release 1.5.0 — identidade híbrida e ajustes de interface

Candidata preparada em 13/11/2026 a partir de `develop`, incorporando `main`
1.4.0 para preservar a documentação e as correções já publicadas. Esta página
não declara deploy, tag ou consolidação de dados em produção.

## Mudanças

- [PR #234 / issue #207](https://github.com/unb-mds/2026-02-UnDb/pull/234): perfil
  institucional prioritário e fallback provisório por nome completo normalizado +
  unidade quando a busca completa não encontra candidato. Risco residual de
  homônimos sem perfil na mesma unidade aceito explicitamente pelo PO.
- Reavaliação seletiva e indicação explícita de perfil público, com nova validação
  na fonte. Promoção para perfil preserva UUID e avaliações; união de UUIDs distintos
  continua administrativa, com bloqueio de colisões.
- Consolidação por conjuntos, commit e progresso por grupo e retomada dos restantes.
  Benchmark local reduziu statements em aproximadamente 72%; não é promessa de
  duração em produção. [Evidências](../estudos/modelo-hibrido-issue-207.md).
- [PR #233 / issue #211](https://github.com/unb-mds/2026-02-UnDb/pull/233): cartões,
  galeria de disciplinas, busca e navbar, fundo de partículas, transições e correções
  de seleção de professor/comentários e destaques. Não muda critérios de avaliação.

## Implantação

1. Publicar backend e frontend compatíveis e aplicar Alembic até `20261113_01`.
   A migration cria `identidades_locais`; não reconcilia os registros existentes.
2. Aplicar como administrador os GRANTs atualizados de
   `scripts/sql/207-acesso-identidades.sql`. O importador precisa de leitura/escrita
   na tabela nova; a API recebe leitura, sem permissão de união de avaliações.
3. Conferir as prévias e os perfis encontrados manualmente antes do fallback.
4. Para consolidar UUIDs antigos, conferir backup completo e restauração, pausar
   API/importadores/outros escritores e usar os comandos administrativos com a
   confirmação explícita de manutenção. Cada grupo concluído tem commit próprio.
5. Conferir fila, avaliações, links antigos, buscas e repetição de importação antes
   de reabrir escritores. Seguir o [procedimento](../identidades-docentes.md).

O merge e o deploy não substituem essa manutenção. Não é necessário repetir toda
a extração da UnB para reavaliar e consolidar o catálogo existente.

## Verificação e publicação

A candidata deve passar pelos checks de CI e revisão humana antes de integrar
`main`. Na candidata, passaram 247 dos 249 testes backend, com dois exclusivos de
PostgreSQL ignorados no modo SQLite, 77 testes frontend e o build estrito do
MkDocs. Na origem, 58 testes dirigidos passaram no PostgreSQL e as migrations
foram verificadas. Os checks de CI da release permanecem uma verificação própria.

Depois do merge, criar a tag da versão no commit integrado e retornar a release
para `develop` por PR. Nenhum desses passos é declarado concluído nesta preparação.

## Reversão

Antes de qualquer associação local, o downgrade da tabela vazia é permitido.
Depois de registrar associações, o downgrade é bloqueado para preservar vínculos
e auditoria. Reverter só o código não desfaz consolidações já confirmadas.
Recuperação de dados exige backup validado e nova janela sem escritores; nunca
apagar aliases ou avaliações manualmente como forma de rollback.
